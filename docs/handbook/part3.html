8. Dependencies between portals

Dependencies decide the build order, and getting them wrong is the most expensive mistake available to us. A portal built before its upstream module exists gets built twice.

8.1 The dependency that applies to everything

Every document in every portal depends on all seven core framework services: authentication and RBAC, organisation and tenancy, document numbering, workflow and approvals, audit, notifications, and attachments. Six of the seven are built. Notifications and attachments are the two gaps, and they are the first thing the lead finishes, in weeks 1 to 6, because everything downstream needs them.

How to work across a dependency without waiting

Two rules from CLAUDE.md make parallel work possible. Reading across modules goes through the other module's published application service — never import another module's SQLAlchemy models, and never join across module tables in a write path. Writing across modules goes through domain events over the transactional outbox: an approved GRN does not call the inventory repository, it emits procurement.grn.approved and inventory subscribes. So agree the event name and payload on day one, and both sides can then build in parallel against it.

9.1 Recommended order of implementation, within any portal

This order is not optional. Every fresher who works back-to-front loses two days.

  1. Read the SRS volume, or write the functional baseline note if none exists. Cite the requirement IDs. If the specification is silent, ask — do not invent a business rule.
  2. Design the data model. Standard columns, soft delete with the deleted_key companion, correct decimal scales, indexes. Get it reviewed before writing the migration.
  3. Write the Alembic migration and prove it runs up and down against a seeded database.
  4. Build the domain layer. Entities, value objects, the state machine, business rules. No FastAPI import, no SQLAlchemy import, no I/O. Unit-test the rules here — this is where coverage is cheap.
  5. Build the application service: use cases, orchestration, DTO mapping. One aggregate per transaction; if you must touch two, modify one and emit an event.
  6. Build the repository and models in infrastructure/.
  7. Expose the API. Pydantic v2 request and response schemas, router, and a declared permission dependency on every endpoint.
  8. Write the integration test against real MySQL in Docker, never SQLite. Include the tenancy test and the 403-without-permission test.
  9. Now wire the front end. Replace the mock import with the API client, keep the layout, delete the mock fixture in the same commit.
  10. Walk the flow end to end in the browser, from the screen that precedes yours to the screen that follows it.

11.3 Individual accountabilities

WhoAccountable for, specifically
D1The stock ledger stays the single truth for quantity and value: every movement writes exactly one ledger row, and valuation reconciles to the general ledger. Maintenance work orders generate correctly from both calendar and meter triggers.
D2The generic master registry stays the way simple masters are added. MRP output reconciles to demand: no phantom shortages, no double-counted scheduled receipts. The production-order release gate never releases without BOM, routing and material.
D3Production entry is one atomic transaction: output, backflushed consumption, scrap and rework either all post or none do. OEE matches a hand calculation for one machine over one shift. Genealogy resolves heat number to bottle in both directions.
D4Debits equal credits, always. The three-way match cannot be bypassed. GST and TDS rates live in master data behind the statutory/ adapter, never in code. The trial balance ties to the sum of ledger rows.
D5The payroll run is reproducible and reversible, and every payslip figure is traceable to attendance, structure and slab. Statutory returns match the filed formats. No salary or bank detail ever reaches a log or an audit row.
