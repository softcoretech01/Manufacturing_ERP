1. How to use this handbook

This is the working document for the six of us building the SSB Manufacturing ERP. It answers five questions, in this order: what screens exist, how they connect, who builds what, in what order, and by when. Read sections 1 to 3 once. Then live in sections 10 to 14 — those are the ones you will come back to every week.

1.1 The one assumption behind every number

This plan estimates the work that remains, not the work from zero

The repository already contains a substantial, working product: 253 screens are routed, and 5 of the 15 portals are wired end to end to a real FastAPI backend. Every duration in section 12 is therefore remaining effort to finish a portal, not the effort to build it from scratch. Section 3 shows the measured status that this rests on, so you can check the basis yourself. If you want a from-zero estimate instead, say so and the numbers change substantially.

1.2 What is in scope for release 1

Thirteen portals. Two are deliberately deferred to release 2: Sales & CRM and the Shop Floor Terminal. Both are marked status: 'PLANNED' in portals.ts, neither has a single screen built, and Sales & CRM has no approved specification (SRS Volume 2 is "Not started"). Building them now would mean inventing business rules, which section 15 explains we must not do. The external Supplier and Customer portals and the React Native mobile app are also release 2.

2. The system in one page

SSB Manufacturing ERP is one connected system for a stainless steel vacuum-insulated water bottle plant. It runs the business from buying steel coil, through production, quality and packing, to dispatch, invoicing and payroll. It is a modular monolith: a single deployable FastAPI application partitioned into modules that map one-to-one onto the SRS volumes, with one React front end on top.

2.1 What a portal is

A portal is the working context a person signs into — not a security boundary. A storekeeper receiving goods works in Inventory; a buyer works in Procurement. Permissions are resolved per user regardless of which portal they are in, server-side, every time. The portal only decides which part of the product they are put in front of, and which sidebar tree they get. This matters to you as a developer for one reason: never treat the sidebar as a control. Hiding a menu item is a convenience. The permission dependency on the endpoint is the control.

Adding a runtime dependency, framework or datastore requires an ADR in docs/adr/ and the lead's approval. This is not negotiable and it is not bureaucracy: a fresher adding a second state library or a second table component is the single fastest way to make 253 screens inconsistent.

2.3 The four rules you will break first

RuleWhy it exists
Soft delete onlyNever DELETE a business row. Set deleted_at and deleted_by. Unique keys carry a generated deleted_key companion column because MySQL treats multiple NULLs as distinct.
Tenancy is application-enforcedMySQL has no row-level security. The base repository injects company_id into every query and every insert. Raw SQL must bind it explicitly; CI greps for text( without a tenant bind.
Public uid, never idURLs and payloads use the ULID uid. The BIGINT id never leaves the database.
No FLOAT for money or quantityQuantity and rate are DECIMAL(18,6), amount is DECIMAL(18,2), percentage is DECIMAL(9,4). Round half-up once, at persistence.

Read this before you feel behind

"UI only" is not zero. Those 81 screens already have their layout, their mock fixture and their TypeScript types written. The mock file in frontend/src/mock/ is a working specification of the shape the API must return. Your job on those screens is to build the backend to match, then delete the mock. That is why five UI-only portals cost 220 person-days and not double that.

3.1 The framework services that are already done

Seven cross-cutting services carry every document in every portal, and all seven are built and working. You do not need to build them, you need to use them:

ServiceWhere it livesWhat you must do
Authentication and RBACmodules/iamDeclare a permission dependency on every endpoint. CI fails an endpoint with none.
Organisation and tenancymodules/organisationResolve TenantContext; let the base repository inject company_id.
Document numberingmodules/numberingAsk the numbering engine for a document number. Never write a sequence in module code.
Workflow and approvalsmodules/workflowCreate a workflow instance for every document, even when the rule is auto-approve.
Audit trailmodules/security, auditEmit audit rows on create, update, submit, approve, reject, cancel, amend. Append-only.
Parametersmodules/parametersRead configurable behaviour from parameters, not from constants in your code.
Reportingmodules/reportingThe one sanctioned place to join across module tables, read-only.
